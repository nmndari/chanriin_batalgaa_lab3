## Алхам 2: Гурван сценарио бичих

Сценарио бүрийг Лекц 3-ын 6 хэсэгтэй формат (Тойм · Системийн төлөв · Орчны төлөв · Гадаад өдөөлт · Шаардлагатай хариу · Хэмжүүр)-аар бичив.

### Сценарио 1 — Performance (`POST /cart/add`)

| Хэсэг | Тайлбар |
|---|---|
| **Тойм** | Хэвийн ачааллын үед хэрэглэгч бараагаа сагсанд нэмэхэд систем хэр хурдан хариулж байгааг шалгана. |
| **Системийн төлөв** | Express API (`server.js`) 3000 порт дээр ажиллаж байна. Нэг инстанс, нэг процесс. Бүх 3 endpoint хэвийн, сүйрээгүй. |
| **Орчны төлөв** | Хэвийн ажлын цагийн ачаалал: **50 виртуал хэрэглэгч (VU)**, тогтмол хурд **~100 хүсэлт/секунд**, туршилтын үргэлжлэх хугацаа **5 минут**. Сүлжээ локал (localhost), CPU/санах ой 70%-иас доош ачаалалтай. |
| **Гадаад өдөөлт** | Хэрэглэгч "Сагсанд нэмэх" товч дарж, `POST /cart/add` хүсэлт илгээнэ (хэвийн хэрэглээний үйлдэл, эвдрэл биш). |
| **Шаардлагатай хариу** | Систем хүсэлтийг хүлээн авч, боловсруулж, `{ok: true, item: 1}` гэсэн HTTP 200 хариуг хэрэглэгчид буцаана. Хүсэлт алдаагүй, хүлээлгийн дараалалд гацахгүй. |
| **Хэмжүүр** | 5 минутын хэмжилтэд: **p95 хариу хугацаа ≤ 150 мс**, **p99 ≤ 300 мс**, алдааны хувь **< 1%**. (k6: `http_req_duration: ['p(95)<150','p(99)<300']`, `http_req_failed: ['rate<0.01']`) |

### Сценарио 2 — Reliability (`POST /pay`)

| Хэсэг | Тайлбар |
|---|---|
| **Тойм** | Хэвийн төлбөрийн үйлдлийн хэдэн хувь нь амжилтгүй болж байгааг (эвдрэлийн давтамж) хэмжинэ. |
| **Системийн төлөв** | API ажиллаж байгаа, сүлжээ тасраагүй. `/pay` endpoint нь дотоод төлбөрийн gateway-тэй холбогддог бөгөөд тухайн gateway тогтворгүй (хүсэлтийн ойролцоогоор 5% нь HTTP 500 `gateway timeout` буцаадаг). |
| **Орчны төлөв** | Хэвийн ажиллагааны горим. **20 VU**, **~30 хүсэлт/секунд**, нийт **≥ 1000 төлбөрийн хүсэлт** илгээж хэмжинэ (статистик ач холбогдол бүхий түүвэр). |
| **Гадаад өдөөлт** | Хэрэглэгч "Төлөх" товч дарж `POST /pay` хүсэлт илгээнэ — **хэвийн хэрэглэгчийн зөв оролт**, санаатай алдаа эсвэл халдлага биш. |
| **Шаардлагатай хариу** | Систем төлбөрийг амжилттай боловсруулж `{paid: true}` бүхий HTTP 200 буцаана. Амжилтгүй тохиолдолд өгөгдөл гэмтээхгүйгээр (мөнгө хасагдахгүйгээр) HTTP 500 буцааж, алдааг логлоно. |
| **Хэмжүүр** | **POFOD (probability of failure on demand) ≤ 0.05**, өөрөөр хэлбэл 1000 хүсэлтэд амжилтгүй хүсэлт **50-иас ихгүй** (error rate ≤ 5%). Мөн амжилттай хариуны **p95 ≤ 200 мс**. (k6: `http_req_failed: ['rate<0.05']`) |

### Сценарио 3 — Availability (сервер гэнэт зогсоод дахин асах)

| Хэсэг | Тайлбар |
|---|---|
| **Тойм** | Сервер гэнэт унасан (crash) үед систем хэр хурдан сэргэж, хэрэглэгчид хэр хугацаанд үйлчилгээ авч чадахгүй байхыг шалгана. |
| **Системийн төлөв** | Node.js процесс `pm2`/`systemd` зэрэг process manager-ын хяналтад ажиллаж байгаа бөгөөд унасан тохиолдолд автоматаар дахин асах тохиргоотой. Хэмжилтийн эхэнд систем хэвийн үйлчилгээ үзүүлж байна. |
| **Орчны төлөв** | Хэвийн ачаалал (**50 VU**, ~100 хүсэлт/с) үргэлжилж байх үед 30 секунд тутам health check илгээгдэж байна. Хэмжилтийн цонх: **30 хоног (сарын ажиллагаа)**. |
| **Гадаад өдөөлт** | **ЭВДРЭЛ:** Node.js процесс гэнэт зогсоно (санах ойн алдаа, `kill -9`, эсвэл серверийн гэнэтийн unplanned restart). Энэ нь хэрэглэгчийн үйлдэл биш, системийн доторх эвдрэл. |
| **Шаардлагатай хариу** | Process manager эвдрэлийг илрүүлж, процессыг автоматаар дахин асаана. Сэргэсний дараа `/cart/add`, `/pay`, `/report` бүх endpoint хэвийн HTTP 200 буцаана. Тасалдлын үед хэрэглэгч 503 хариу авах ба өгөгдөл алдагдахгүй. Эвдрэлийг мониторинг руу мэдэгдэнэ. |
| **Хэмжүүр** | **Availability ≥ 99.9%** сард (зөвшөөрөгдөх нийт тасалдал ≤ 43 минут/сар). **MTTR (сэргэх хугацаа): p95 ≤ 30 секунд, p99 ≤ 60 секунд** нэг эвдрэлд. Health check амжилтгүй болсноос эхлээд дараалсан 3 амжилттай health check хүртэлх хугацаагаар хэмжинэ. |

### Өөрийгөө шалгах: "Сайн сценариогийн 5 шинж"

| Шинж | Сценарио 1 (Performance) | Сценарио 2 (Reliability) | Сценарио 3 (Availability) |
|---|---|---|---|
| **Итгэмжтэй** (бодитоор биелэх боломжтой) | Хоосон хариу буцаадаг хөнгөн endpoint тул 150 мс бодитой | Gateway-ийн бодит 5% алдааны түвшинтэй нийцүүлсэн | pm2 restart нь ердийн 5–20 сек, 30 сек нөөцтэй |
| **Үнэ цэнэтэй** (бизнест ач холбогдолтой) | Сагс удаан бол хэрэглэгч худалдан авалтаа орхино | Төлбөр амжилтгүй бол шууд орлогын алдагдал | Систем унавал бүх борлуулалт зогсоно |
| **Тодорхой** (хэн, юуг, хаана) | Хэрэглэгч → `POST /cart/add` → API сервер | Хэрэглэгч → `POST /pay` → төлбөрийн gateway | Эвдрэл → Node процесс → process manager |
| **Нарийн** (тоон утгатай) | 50 VU, 100 rps, p95 ≤ 150 мс, p99 ≤ 300 мс | 1000 хүсэлт, POFOD ≤ 0.05 | 99.9%/сар, MTTR p95 ≤ 30 сек |
| **Ойлгомжтой** (хэмжих арга нь тодорхой) | k6 `http_req_duration` threshold | k6 `http_req_failed` rate | Health check log-оос uptime ба сэргэх хугацаа |
